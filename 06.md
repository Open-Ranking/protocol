# ORE-06

## The `/reputation` Endpoint

`draft` `optional`

This document defines the `/reputation` endpoint, which returns a structured reputation profile for a single Nostr pubkey. Unlike `/rank`, this endpoint is designed for detailed inspection of a single identity and returns richer structured data beyond a simple rank. It maps naturally to a full profile detail screen in a client UI.

---

## Capability Document

This endpoint follows the standard capability document structure defined in [ORE-01](01.md). Algorithms on this endpoint MAY declare `"pov": true` to indicate that they require a `pov` pubkey in every request.

---

## Endpoint

```
POST /reputation
```

Returns a structured reputation profile for the given pubkey according to the requested algorithm.

## Request

| Field | Type | Required | Description |
|---|---|---|---|
| `pubkey` | string | yes | The pubkey to assess. MUST follow the format defined in [ORE-00](00.md). |
| `algorithm` | string | no | The algorithm to use. If omitted, the provider MUST use the default algorithm for this endpoint as defined in [ORE-01](01.md). |
| `pov` | string | no | A point-of-view pubkey for personalised algorithms. MUST be provided if the requested algorithm requires it, as declared in the capability document. |

### Example Request

```json
{
  "pubkey": "a3f9c...",
  "algorithm": "pagerank"
}
```

## Response

The response is a JSON object. The `pubkey` and `rank` fields are always present. All other fields are optional and MAY be omitted by the provider depending on the algorithm and available data.

| Field | Type | Required | Description |
|---|---|---|---|
| `pubkey` | string | yes | The pubkey that was assessed, as provided in the request. |
| `rank` | number | yes | The rank assigned to this identity by the requested algorithm. Higher values are always better. The scale and range are defined by the algorithm. |
| `categories` | array | no | An array of category objects describing the nature of the content published by this identity. See the Categories section below. |
| `stats` | object | no | An object containing integer counts derived from the provider's index. See the Stats section below. |
| `x` | object | no | A provider-specific object for arbitrary additional data. See the Provider Extensions section below. |
| `ttl` | integer | no | A hint indicating how many seconds the response is expected to remain valid. Clients MAY cache the result for this duration. Clients MUST treat this value as a hint, not a guarantee. |

---

## Categories

The `categories` field is an array of objects, each describing a content classification assigned to this identity by the provider.

| Field | Type | Required | Description |
|---|---|---|---|
| `label` | string | yes | A content label. MAY be a well-known label as defined below, or a free-form string for informational purposes. |
| `confidence` | number | yes | The provider's confidence in this classification, as a float between 0 and 1. Higher values indicate greater confidence. |

### Well-known labels (WIP)

The following label namespaces are defined by this ORE and carry programmatic meaning. Clients MAY use these to drive UI behaviour such as blurring avatars or displaying content warnings.

**`nudity:`**

| Label | Meaning |
|---|---|
| `nudity:suggestive` | Suggestive content, not explicitly sexual. |
| `nudity:explicit` | Explicit nudity or pornographic content. |

**`violence:`**

| Label | Meaning |
|---|---|
| `violence:suggestive` | Mild or implied violence. |
| `violence:graphic` | Graphic or disturbing violent content. |

Labels outside these namespaces are free-form and informational only. Clients SHOULD NOT drive programmatic behaviour from unrecognised labels. Providers SHOULD NOT invent new well-known label namespaces without a ratified ORE.

### Example

```json
"categories": [
  { "label": "bitcoin", "confidence": 0.91 },
  { "label": "nudity:suggestive", "confidence": 0.61 }
]
```

---

## Stats (WIP)

The `stats` field is an object containing integer counts derived from the provider's index. All values MUST be non-negative integers. Providers MAY include any integer count that is meaningful for the given pubkey and algorithm. The following fields are well-known:

| Field | Type | Description |
|---|---|---|
| `followers` | integer | The number of followers in the provider's indexed follower set. |
| `follows` | integer | The number of pubkeys this identity follows, as known to the provider. |

Providers MAY include additional integer fields beyond those listed above. Clients MUST ignore unrecognised fields in `stats`.

### Example

```json
"stats": {
  "followers": 1400,
  "following": 320,
  "posts": 8741
}
```

---

## Provider Extensions

The `x` field is a flat object reserved for provider-specific data that does not belong to any ratified ORE. Its contents are entirely provider-defined and carry no protocol-level semantics.

For the sake of interoperability, clients SHOULD NOT rely on the contents of `x` for any functional behaviour. Clients MAY display its contents to power users or use it for debugging. Providers MUST NOT use `x` to shadow or override any standard field defined in this or any other ORE.

### Example

```json
"x": {
  "myprovider-trust-score": 42,
  "verified-by-myprovider": true
}
```

## Full Example Response

```json
{
  "pubkey": "a3f9c...",
  "rank": 0.91,
  "categories": [
    { "label": "bitcoin", "confidence": 0.91 },
    { "label": "nudity:suggestive", "confidence": 0.61 }
  ],
  "stats": {
    "followers": 1400,
    "following": 320,
    "posts": 8741
  },
  "x": {
    "twitter-handle": "@user"
  },
  "ttl": 3600
}
```

## Errors

Algorithm selection, pov validation, and their associated error codes follow the rules defined in [ORE-01](01.md).

| Status | Reason |
|---|---|
| `400` | The request body is malformed or not valid JSON. |
| `422` | The `pubkey` field is missing or invalid. |
| `422` | The requested algorithm is not supported by this endpoint. |
| `422` | The requested algorithm requires a `pov` but none was provided. |
