# ORE-01

## Capability Document

`draft` `mandatory`

This document defines the capability document that every Open Ranking provider MUST expose. It allows clients to discover which endpoints and algorithms a provider supports.

---

## Endpoint

```
GET /.well-known/open-ranking
```

Providers MUST serve the capability document at this well-known location. The response MUST have a `Content-Type: application/json` header and a `200` status code.

---

## Structure

The capability document is a JSON object. Each key is a supported endpoint path (e.g. `/reputation`). Each value is an object with an `algorithms` array describing the algorithms available for that endpoint.

```json
{
  "/reputation": {
    "algorithms": [
      {
        "id": "pagerank"
      },
      {
        "id": "personalized-pagerank",
        "source": true
      }
    ]
  },
  "/recommendations": {
    "algorithms": [
      {
        "id": "random-pubkeys",
      }
    ]
  }
}
```

---

## Algorithms

The `algorithms` field MUST be a non-empty array. Each entry MUST contain an `id` field. The `id` MUST follow the algorithm identifier rules defined in ORE-00.

The **first** algorithm in the array is the default for that endpoint. Clients that do not specify an algorithm in their requests MUST be served the default.

### Source

Algorithms are either global or personalized. A personalized algorithm requires a `source` pubkey representing the user's perspective, for example to compute a trust-weighted ranking relative to that user.

If an algorithm requires a source, it MUST declare `"source": true` in the capability document. If `source` is absent or `false`, the algorithm is global and does not use a source.

Providers MUST respond with `422 Unprocessable Content` if a request does not include a `source` for an algorithm that requires one. Providers SHOULD include a human-readable explanation in the `X-Reason` header.

Clients MUST NOT send a `source` to a global algorithm. If a `source` is sent to a global algorithm, the provider MUST ignore it.

### Variants

Providers SHOULD express algorithm variants as distinct named algorithms rather than as configurable parameters. Provider-specific configuration beyond what this protocol defines is explicitly out of scope and MUST NOT be part of the capability document.

---

## Algorithm selection

Clients MAY specify a preferred algorithm in a request. If no algorithm is specified, the provider MUST use the default algorithm for that endpoint. If the requested algorithm is not supported by the specific endpoint, the provider MUST respond with `422 Unprocessable Content`.
