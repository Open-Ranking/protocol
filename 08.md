# ORE-08

## The `/leak/pubkeys` Endpoint

`draft` `optional`

This document defines the `/leak/pubkeys` endpoint, which accepts a list of pubkeys and returns cryptographically attested leak records for any of them whose private key is known to have been compromised.

---

## Background

A Nostr identity is fully controlled by its private key. If an `nsec` is exposed publicly, for example by being accidentally posted as a Nostr event, anyone who finds it can impersonate that identity indefinitely. There is no revocation mechanism in Nostr; the only recourse is (manual) key rotation.

Providers that index Nostr events can detect these exposures and publish attestations, enabling clients to warn users before they interact with a compromised identity.

## Endpoint

```
POST /leak/pubkeys
```

Accepts a list of pubkeys and returns a leak record for each one that is known to be compromised. Pubkeys with no known leak are omitted from the response to save bandwidth.

## Proof

A leak proof is a Schnorr signature produced by signing a fixed message with the leaked private key. This allows any verifier to confirm the claim independently using only the public key.

The message to sign is the UTF-8 string:

```
this-key-was-leaked-<pubkey>
```

where `<pubkey>` is the 64-character lowercase hex encoding of the public key associated with the leak private key.

The proof is the resulting 64-byte Schnorr signature, encoded as a 128-character lowercase hex string.

## Leak Object

| Field | Type | Required | Description |
|---|---|---|---|
| `status` | string | yes | Either `"confirmed"` or `"suspected"`. `"confirmed"` means a valid proof is present. `"suspected"` means the provider has strong evidence of compromise, but no proof. Clients MAY choose to trust or ignore suspected leaks at their discretion. |
| `detected_at` | integer | yes | Unix timestamp of when the provider first detected the leak. |
| `proof` | string | no | The 128-character lowercase hex Schnorr signature described above. MUST be present when `status` is `"confirmed"`. MUST be omitted when `status` is `"suspected"`. |

## Request

| Field | Type | Required | Description |
|---|---|---|---|
| `pubkeys` | array of strings | yes | The pubkeys to check. MUST contain at least one element. Each pubkey MUST follow the format defined in [ORE-00](00.md). |

### Example Request

```json
{
  "pubkeys": [
    "a3f9c...",
    "b7e2d...",
    "cc481..."
  ]
}
```

## Response

The response is a flat JSON object mapping each pubkey with a known leak directly to its Leak Object. Pubkeys with no known leak are omitted. If no leaks are known for any of the requested pubkeys, the response MUST be an empty object.

### Request size

Clients SHOULD NOT send more than 1000 pubkeys in a single request. Providers MAY enforce their own limit and SHOULD respond with `413 Payload Too Large` if the request exceeds it.

### Example Response

```json
{
  "b7e2d...": {
    "status": "confirmed",
    "detected_at": 1700000000,
    "proof": "2a9f..."
  },
  "cc481...": {
    "status": "suspected",
    "detected_at": 1701000000
  }
}
```

## Success Codes

| Status | Description |
|---|---|
| `200` | The result is ready and the response body contains the result. |
| `202` | The result is not yet available. Clients MUST retry the identical request after the number of seconds indicated by the `Retry-After` response header. |

All endpoints in this protocol are effectively read-only queries. Retrying an identical POST request is safe.

## Error Codes

| Status | Reason |
|---|---|
| `400` | The request body is malformed or not valid JSON. |
| `413` | The number of pubkeys in the request exceeds the provider's limit. |
| `422` | The `pubkeys` array is missing or empty. |
| `422` | One or more entries in `pubkeys` are not valid pubkeys. |
